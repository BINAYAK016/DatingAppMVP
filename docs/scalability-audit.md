# Sangai database and query audit

Status: initial audit and query foundation completed, with 13 isolated regression tests and the combined 56-test API suite passing. One bounded local read smoke test completed. Source baseline: `35fd0d3` on `feat/sangai-redesign`; implemented API checkpoint: `a4d5193`. Audit dates: 1–2 October 2026. See [verification](verification.md) for final mobile/browser/native checkpoints. The earlier Meet Me proposal and historical verification notes remain preserved.

The initial audit inspected code, live local schema/index metadata and bounded SELECT query plans read-only. Query regressions and the load API used owned disposable databases. The later coordinated local beta upgrade applied additive migrations while preserving persistent volumes; its backup/restore and native evidence are recorded in [verification](verification.md). Live selfie verification remains an external-provider proposal, not an implemented feature.

## What exists and should remain

The backend is one NestJS process with a controller in `main.ts` and function modules for identity, discovery, social content, interactions, games, media, push and account export. PostgreSQL 17 stores sessions and authoritative social state. Parameterized SQL, database uniqueness constraints, ordered connection pairs, transaction-scoped mutation locking and migration checksums provide useful foundations. Keep the modular monolith and these correctness protections.

Discovery respects both people's explicit preferences and excludes blocks/closed connections. Incoming Likes are hidden. Social posts, stories and media are subject to match and audience checks. Feed and conversation endpoints already use timestamp/UUID cursors. Messages and multi-photo post publication have retry identifiers. Reuse these contracts and test their privacy boundaries during optimization.

Realtime means polling: the baseline mobile store refreshes the complete `/state` every 12 seconds while active; focused chat and legacy game screens fetch conversation data every 3 seconds; selected-match legacy game readiness is renewed/read every 10 seconds; story refreshes also request state. The implemented changes coalesce state/GET requests and add direct Games 2.0 session polling (four seconds while playing, ten seconds while invited, with failure backoff up to 30 seconds). There is no WebSocket server, Redis, shared cache or general durable processing queue. Shared PostgreSQL file-deletion jobs and push claims now provide scoped durable work. A websocket adapter cannot be audited as if it already exists.

Media is private local filesystem storage. The API admits bounded uploads, buffers them, performs Sharp/ffmpeg processing on the request path, and authorizes/streams each image, thumbnail and video range through the API. Cleanup runs every minute in each API process; push dispatch runs every 15 seconds. These in-process schedules now use shared PostgreSQL deletion/claim records. Compatible shared storage, independent worker deployment and multi-instance operation remain unverified.

## Implemented query-foundation indexes and later candidates

Migration `008_query_foundation.sql` adds these six indexes. Isolated tests, the bounded harness and the combined API suite used them; the local beta upgrade also applied them. Larger-data plan validation remains pending:

- `comments(post_id, created_at DESC, id DESC)` for bounded per-post pages.
- `messages(recipient, sender)` with `WHERE read_at IS NULL` for batched unread summaries.
- `stories(author, created_at DESC, id DESC)` for matched-author pages, plus `stories(expires_at)` for cleanup if plans justify both.
- `posts(author, created_at DESC, id DESC)` for own posts and matched-author feed retrieval.
- `saved_posts(actor, created_at DESC, post_id DESC)` for a stable saved-post cursor.

Subsequent measured work may justify canonical-pair timeline indexes for messages/snaps/plans/games; reverse connection endpoint indexing; session/user/expiry and media-reference indexes; and a selective eligible-user candidate index. Do not add the entire list blindly. Multicolumn indexes depend on their leading predicates, and partial indexes must match the query condition. [PostgreSQL multicolumn guidance](https://www.postgresql.org/docs/17/indexes-multicolumn.html), [partial-index guidance](https://www.postgresql.org/docs/17/indexes-partial.html)

Current migrations run inside one transaction with a migration advisory lock and checksum validation. This is useful for the beta. Large-table concurrent index creation cannot be inserted into that transaction: plan a separate controlled production migration step when warranted. [PostgreSQL concurrent index restrictions](https://www.postgresql.org/docs/17/sql-createindex.html)

## Implemented query foundation

The query changes are in `db.ts`, `social.ts`, `moments.ts`, the conversation cursor lines in `interactions.ts`, `008_query_foundation.sql`, `test/scalability.test.ts` and `test/read-load.ts`, with route wiring in `main.ts`. They preserve discovery, authentication, chat mutation/read-state and game business rules.

1. Add `readTx` with `REPEATABLE READ READ ONLY`, explicit rollback/release and no social mutation advisory lock. Use it only for pure state/feed/detail/saved reads. Retain `tx` unchanged for mutation correctness. A snapshot gives consistent permissions within the request; it is not permission to cache private content indefinitely.
2. Move story eligibility before its limit and batch author lookups. Preserve response shape and current privacy predicates.
3. Batch match unread/latest-message summaries, retaining existing match ordering and fields.
4. Introduce a batched post projection and keep the single-post wrapper for compatibility. Aggregate visible reactions in SQL, fetch authors/media/save state in batches, and bound visible comments per post. Test parent/reply filtering and self-author semantics explicitly.
5. Add the six reviewed indexes and additive match/story/notification cursor helpers with limits of 1–50, stable UUID tie-breakers and exact timestamp precision. Legacy state retains its compatible match collection; this does not make the entire bootstrap bounded.
6. Preserve PostgreSQL microseconds in existing feed and mixed conversation `created_at` ordering keys; JavaScript Date conversion previously truncated them and could skip same-millisecond rows on the next page. Existing timestamp/UUID client cursors remain usable without a contract rewrite.

Mobile `activity.tsx` now uses 30-item notification pages with exact returned cursors, ID deduplication, virtualized rows, older-page loading and focus/foreground refresh. It retains loaded rows on temporary failures, clears them on 401/403/session change and keeps resource-based Game links and read-all behavior. Initial match/story UI and legacy state still use their existing collections: adding these endpoints does not make bootstrap bounded or expose complete story/match paging in the app. All three focused Activity browser checks passed on the fresh local export in installed Chrome in 11.8 seconds with no failures/skips, using intercepted synthetic notification GET/POST fixtures. Evidence output is `artifacts/ui-activity-pagination`; see [verification](verification.md) for the scoped Android Activity checks and remaining device matrix.

Isolated regression coverage: story starvation, unrelated-user read concurrency while the mutation lock is held, transaction rollback/release, current-match/block/demo/suspension/audience filtering, visible reaction counts, hidden/visible reply parents, deterministic cursor ties and query counts that do not grow per returned author/reactor. Retain all existing discovery, chat retry, snap expiry, media privacy and game answer-secrecy tests. Removing mutation serialization without those invariants is outside this proposal.

Executed Stage 3 verification: the initial 11 isolated `test/scalability.test.ts` tests passed in 28.8 seconds; after adding feed/chat precision regressions, all 13 passed in 7.94 seconds with no failures or skips. Current API typecheck/build and scoped Activity typecheck/lint passed. The tests cover more than 200 unrelated newer stories, reads while an unrelated mutation holds the advisory lock, read-only rejection and repeatable permission snapshots, privacy/answer projections, reply ancestors, exact-microsecond cursor ties, 65 same-millisecond posts across feed pages, 70 mixed message/snap/game/plan items across history pages, duplicate match names and rejected invalid cursors. Instrumenting actual `PoolClient.query` calls measured 18 state calls for both a small fixture and a larger fixture with 41 matches, 30 posts and 41 visible comments/reactors. Constant query count does not imply constant scanned rows, response size, CPU or production latency. The final combined API suite passed 56/56. The coordinating browser suite passed 52/52; exact final native scope is recorded in [verification](verification.md).

On 1 October 2026 at `17:31:20 UTC`, the bounded read harness completed 100 authenticated GETs over 9.933 seconds against an owned disposable API/database: four paced workers, offered 10 requests/second, zero errors and 20 HTTP 200 responses for each of state/feed/matches/stories/notifications. Endpoint p95 ranged from 28.155 to 79.935 ms. Raw results are outside Git at `outputs/load-qa/read-load-1790875866648.json` in the task workspace. The fixture had five users, three connections, one message, three posts, one story and no games. See [capacity-plan.md](capacity-plan.md) for all percentiles, the runnable command and important measurement limits.

## Evidence and limits

Read-only local metadata and SELECT plans were collected on 1 October 2026; the final audit time marker was `2026-10-01 16:59:56 UTC`. The database contained 6 users, 5 connections, 25 messages, 3 stories, 20 posts, 0 comments, 2 reactions, 41 media, 23 games and 73 notifications. PostgreSQL catalog estimates were stale or unset for some tables, so actual counts were queried separately.

Six representative component SELECT plans were run inside `BEGIN READ ONLY` with a five-second local statement timeout and rollback. They showed comment/story/unread/snaps scan-and-sort shapes, a user/connection hash join for match fanout, and saved-post bitmap lookup followed by sorting. Their measured execution times were approximately 0.078–0.301 ms on this tiny dataset. Sequential scans are often correct for tiny tables; these numbers are neither an endpoint latency benchmark nor proof of a production bottleneck threshold. No high-volume isolated data, lock-contention test or load test was run in Stage 1. [How to interpret EXPLAIN](https://www.postgresql.org/docs/17/using-explain.html)

Runtime resources, workload assumptions, proposed load tests and the staged modular-monolith roadmap are recorded in [capacity-plan.md](capacity-plan.md).

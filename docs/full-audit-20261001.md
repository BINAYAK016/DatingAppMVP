## A. Executive summary

Sangai remains a native Android/iOS private beta for Nepali adults, with Discover, Chat, Sangai and Profile. It uses Expo 57/React Native 0.86, NestJS and PostgreSQL in a modular monolith. Mutual matching, hidden incoming Likes, private social audiences, view-once snap expiry, date consent and the no-AI boundary remain intact.

The confirmed newly attached media deletion race is fixed with synchronized cleanup and a durable file-deletion ledger. Stories now apply current eligibility before their limit. Pure projections no longer take the global mutation lock; match and post projections are batched. Activity uses a bounded notification cursor API. Feed and chat preserve exact PostgreSQL timestamps between pages.

Games 2.0 implements all seven mechanics with asynchronous invitations, explicit guest acceptance, immutable locked answers, private reveals, durable retry IDs/revisions and resource notifications. Ready is advisory for v2. Legacy games remain supported, and a feature flag permits a safe rollback without deleting sessions.

The current full API suite passed **56/56** in **90.811 seconds**. That is correctness evidence for the tested contracts, not production capacity or native platform parity. The bounded load smoke run used only five synthetic users and completed 100 reads without errors. Section I records the coordinating task's final combined mobile typecheck/lint, all-platform export, browser and native verification status.

No real liveness provider, paid checkout, deployed Redis, WebSocket service or private object store was introduced. Production remains guarded. Public moderation, external-provider delivery, physical iOS execution and representative high-cardinality/load tests are still required.

## D. UI/UX and product-loop audit

**U03 — P1 / HIGH, fixed: Game → Chat overwrote an unsent draft.** PROBLEM: Talk about it replaced a previously typed Chat draft with the game starter. WHY: replacing the route created a fresh Chat instance instead of returning to the existing one. USER IMPACT: an unfinished message disappeared. BUSINESS IMPACT: the feature meant to start conversation damaged trust in messaging. TECHNICAL IMPACT: per-screen draft state was bypassed by duplicate navigation. FIX: dismiss to the existing conversation and consume a game starter only into an empty composer; never send either text automatically. A focused browser regression reproduced the loss before the correction; final verification is recorded in section I. The navigation uses the documented [Expo 57 Router dismissTo contract](https://docs.expo.dev/versions/v57.0.0/sdk/router/).

**U04 — P2 / MEDIUM, fixed: Android connection failures exposed internal transport text.** PROBLEM: the inline game error showed `fetch failed: java.net.ConnectException` during a controlled local API outage. WHY: the network classifier covered browser fetch wording but omitted the native Android format. USER IMPACT: the error was difficult to understand even though the selected private answer remained intact. BUSINESS IMPACT: testers could mistake a recoverable connection problem for lost game progress. TECHNICAL IMPACT: raw adapter errors escaped the shared request boundary. FIX: recognize the native transport forms and use a concise connection/retry message. A browser regression injects the exact observed Android error and checks retained draft/progress plus explicit refresh; section I distinguishes that regression from final native checks.

**U05 — P1 / HIGH, fixed: a sent Chat message could remain below the viewport.** PROBLEM: the full journey test found the new message outside the visible area in a long conversation containing completed game cards. WHY: list growth and scroll-anchor work reset the near-bottom flag before a scheduled scroll, cancelling the user's explicit-send handoff. USER IMPACT: a successful message looked missing until the user scrolled. BUSINESS IMPACT: uncertainty about sends damages the app's central conversation loop. TECHNICAL IMPACT: virtualized row measurement raced ordinary reader-position preservation. FIX: track the confirmed message ID and access generation, follow its authorized refreshed row through layout until it is visible, and cancel that intent on manual browsing, focus loss or revoked access. Normal incoming refreshes preserve older reading position. The focused regression uses long synthetic history and a tall game card; it never scrolls the test after Send. Definitive send authorization failures also clear private content immediately and avoid claiming that the draft remains.

**U06 — P1 / HIGH, fixed: interrupted message animations left text invisible.** PROBLEM: the `0b74d51` Android candidate saved and scrolled a new message correctly, but its bubble remained transparent until Chat was reopened. WHY: the recent-message fade started at opacity zero; animation cleanup and reduced-motion skip paths did not restore it. The emulator's existing animation scale was zero, so late accessibility resolution interrupted the fade. USER IMPACT: a successfully sent message appeared missing. BUSINESS IMPACT: hidden messages undermine confidence in Chat. TECHNICAL IMPACT: a mounted keyed row retained an interrupted animated value, which browser viewport checks did not detect. FIX: start from readable opacity 0.75, restore full opacity on every effect/skip/cleanup, and prevent stale completion callbacks from changing a newer animation. A deterministic browser test changes reduced motion during the entrance and measures effective opacity; final native checks retain the emulator's disabled-animation setting.

The four-tab connection loop remains the product foundation. Games live in Chat through Play together and a Quick Play chooser; selecting a game requires Send Invite. The room shows the permitted action, saved progress, waiting state and private reveal. Talk about it prepares a conversation starter without sending it. Existing feed, story, snap and date flows retain their audience/consent rules.

**U01 — P1 / MEDIUM, partial: recovery and platform confidence.** PROBLEM: source checks and browser fixtures do not establish camera, permission, keyboard, media-background and restored-draft behavior on every native device. WHY: this Windows workflow cannot execute physical iOS, and external providers are not configured. USER IMPACT: a tester may reach a platform-specific dead end. BUSINESS IMPACT: unreliable onboarding or return-to-chat loses trust before the connection loop works. TECHNICAL IMPACT: lifecycle, native SDK and configuration failures can escape bundle checks. FIX: complete the final Android journeys, then a documented physical Android/iOS permission/network/media matrix; retain content for transient failures and clear it for revoked access. Do not label unexecuted scenarios passed.

**U02 — P2 / MEDIUM, open: product measurement and scope.** PROBLEM: there is no agreed analytics design proving which parts of onboarding, discovery, chat and games improve return conversations. WHY: earlier increments prioritized feature breadth and local behavior. USER IMPACT: unnecessary steps or unclear invitations may remain. BUSINESS IMPACT: retention and subscription assumptions cannot be validated. TECHNICAL IMPACT: adding trackers without a data plan risks collecting private relationship/answer content. FIX: agree minimal consent-aware events and success measures before implementing analytics; measure core-loop completion and recovery, not compatibility or private answers. Meet Me remains an approved separate design plan; do not treat the proposal as delivered.

Pricing is still Free plus Sangai Plus preview only. Seven standard games remain Free. NPR 299/AUD 7.99 and annual discounts are hypotheses, not validated conversion, revenue or infrastructure funding.

## E. Security, privacy and operational safety

The implementation preserves verified account access/profile gates, hidden Likes, server-authoritative matching, blocks/unmatch, private purpose-specific media and mechanic-specific secret projections. Email verification and an 18+ declaration do not prove age or identity. Messages remain server-readable, not end-to-end encrypted. Already delivered bytes/screenshots cannot be recalled.

The [security foundation](security-foundation.md) documents shared quotas, file deletion, upload bounds and push claims. Account deletion commits account removal plus file obligations; immediate draining is best effort, and failed file jobs remain for retry/investigation. A worker must see the same compatible storage as the database's media paths. Push uses bounded at-least-once attempts; provider acceptance is not receipt, and a crash after acceptance can cause duplicate delivery.

**S03 — P1 / HIGH, fixed: delayed Chat reads could restore content after revoked access.** PROBLEM: an in-flight main conversation, history or snap read could return after a newer authorization failure cleared the screen. WHY: the initial lifecycle guards covered session identity or request sequence without consistently invalidating every prior access scope. USER IMPACT: private conversation content could reappear after its relationship access was revoked. BUSINESS IMPACT: block/unmatch trust depends on consistent visible revocation. TECHNICAL IMPACT: a formerly authorized snapshot could overwrite newer cleared state even though the server correctly rejected the later action. FIX: capture the Chat access generation for main/history/snap reads, invalidate it on definitive access failures, clear private UI state and ignore older success/error responses. Tests exercise delayed history and a held main GET released after Send receives 403. This prevents client resurrection; it cannot recall bytes or screenshots already delivered.

**S01 — P1 / HIGH, open: public safety and retention operation.** PROBLEM: a local moderator console and database controls do not constitute a staffed public dating safety service. WHY: policies, ownership, escalation, backups and retention operation are not deployed/validated. USER IMPACT: harm reports or deletion failures may lack timely resolution. BUSINESS IMPACT: a public launch can create obligations the small team cannot meet. TECHNICAL IMPACT: backups, moderation records, storage reconciliation and persistent job failures need controlled access and procedures. FIX: agree the production safety/retention model, test escalation and backup restore, review moderation access, monitor unresolved file jobs and retain the production guard until that operation is reviewable.

**S02 — P1 / HIGH, open: real providers and liveness.** PROBLEM: no genuine live-selfie result or configured external Google/SMTP/push delivery has been verified. WHY: provider selection, credentials and device/configuration decisions remain pending. USER IMPACT: identity claims would be misleading and external signup/recovery may fail. BUSINESS IMPACT: trust, provider cost and biometric responsibility cannot be inferred from local demos. TECHNICAL IMPACT: native compatibility, server result validation, reference-photo comparison, retention/deletion, failure/retry and spoof resistance need a real integration. FIX: review a concrete no-government-ID provider proposal before introduction; perform a native SDK spike and genuine live/reference comparison with explicit consent and minimal retention. Configure and verify actual auth/email/push flows separately. Never substitute a demo success for a live result.

## F. Scalability, infrastructure and business limits

**Q01 — P1 / HIGH, partial: mutation serialization and account fanout.** PROBLEM: one mutation advisory lock still serializes unrelated social changes; legacy state includes all matches, and conversation hydration makes per-item reads. WHY: correctness currently relies on a simple shared lock and backward-compatible bootstrap. USER IMPACT: slow work can delay messages/actions. BUSINESS IMPACT: latency and repeated database work raise cost before meaningful growth. TECHNICAL IMPACT: constant query count does not bound scanned rows, response bytes, CPU or pool wait. FIX: move mobile match/story callers onto usable cursors and lean focused/bootstrap contracts, batch typed chat hydration, measure selective candidate/content plans and replace mutation locking with an ordered entity/pair scheme only after privacy/race regressions. Older saved/comment/history lists need complete cursor contracts rather than silent truncation.

**Q02 — P1 / HIGH, partial: media/jobs and deployment boundaries.** PROBLEM: private bytes and request-path image/video processing remain tied to local storage and API processes. WHY: the beta has no deployed object store or independent processing queue. USER IMPACT: growth or a disk/process fault can delay media and cleanup. BUSINESS IMPACT: bandwidth/transcoding/disk costs and recovery ownership are unknown. TECHNICAL IMPACT: replicas with isolated disks cannot safely authorize/serve/drain the same media paths; timers alone do not establish worker supervision or resource isolation. FIX: measure bytes/durations/processing and connection budgets, then introduce reviewed shared private storage, durable processing claims and independently bounded workers; test restart, drain, rollback, missing files and immediate block/expiry strategy before adding replicas.

**Q03 — P2 / MEDIUM, partial: observability and service objectives.** PROBLEM: sanitized per-instance metrics exist without aggregation, alerts, agreed latency/error objectives or product analytics. WHY: operational instrumentation is an initial foundation. USER IMPACT: prolonged failures may be discovered late. BUSINESS IMPACT: neither cost nor a capacity promise can be defended. TECHNICAL IMPACT: process restarts erase local totals; event-loop/pool/lock/job/provider bottlenecks need correlated evidence. FIX: agree objectives and data minimization, collect sanitized endpoint/pool/lock/job metrics and alert on sustained errors/backlogs, then use realistic paced/open-load and failure tests. Do not select thresholds after a run to make it pass.

There is no measured 100K, 1M or 10M deployment capacity. Registered accounts are dataset size, not concurrent users. Keep PostgreSQL and the modular monolith; split services or shard only for a demonstrated workload/ownership boundary.

## G. Games 2.0: actual rules and contracts

| Game                    | Implemented rules                                                                                                        | Completion / private reveal                                                                                                                   |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------- |
| This or That            | Five binary choices per player                                                                                           | Both finish; each question reveals only after both lock it                                                                                    |
| Would You Rather        | Five playful binary choices per player                                                                                   | Both finish; joint locks reveal that question                                                                                                 |
| Two Truths & a Lie      | Host authors three distinct statements plus a private invented index; guest guesses; roles then swap                     | Two author/guess turns; statements are visible to the guesser, invented index waits for the locked guess                                      |
| Guess My Answer         | Six alternating turns; author privately chooses one of four options, partner guesses                                     | Six guesses; answer stays private until its guess locks                                                                                       |
| Compatibility Challenge | Six lifestyle/communication choices per player                                                                           | Both finish; actual shared/different choices only, no compatibility percentage                                                                |
| 20 Questions            | Twenty alternating ask/answer exchanges; custom or suggested question; 180-character questions and 500-character answers | Twenty completed exchanges, with role/turn validation                                                                                         |
| Rapid Fire              | Each player explicitly starts an independent 90-second server timer; up to ten binary answers; early Finish permitted    | Both finish or started timers end; comparisons include only mutually answered questions; an unstarted player can return before session expiry |

Only current mutually matched participants can read or act. An invitation lasts 24 hours; only its guest can accept/decline. Acceptance starts a seven-day session; either person can cancel. Ready is selected-match-only and advisory for v2, never a consent or online-presence assertion. Legacy v1 retains its historical Ready/two-minute/ten-minute rules.

Definitions and sessions are versioned. Locked answers are immutable. Durable action IDs, canonical hashes and revisions distinguish an accepted retry from conflicting input or stale state; notification resource IDs/dedupe keys open the authorized room without embedding answers. Reports and own-account export omit the partner's hidden answers. Incomplete expiry does not publish a completed reveal.

Play again and Try another game lead to explicit Send Invite. Game-to-Chat prompts use an account/server/target-scoped unsent draft; Chat consumes it only if the composer is empty, and the person must send it. Private prompt text is not put in route URLs. Native drafts use SecureStore; web sessionStorage is not an encrypted vault.

Server `ENABLE_GAMES_V2=false` disables catalog/creation/non-cancel v2 actions while authorized existing reads and cancellation remain available; deadline maintenance continues. Keep the migrated schema and compatible binary. Do not drop game/event/result rows or deploy a pre-v2 binary as rollback. See [full game contracts and rollout](games-v2.md).
